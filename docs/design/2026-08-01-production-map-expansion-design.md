# 96×96 玩具のまち拡張 設計

**日付:** 2026-08-01

**状態:** 実装済み・ローカル検証済み・公開検証待ち

**対象:** world bounds、追加2地区、道路、静的ランドマーク、物理、telemetry、E2E、chunk判断

## 1. 目的

既存72×72の中央車庫＋4地区と15件の仕事を壊さず、箱庭を96×96へ拡張する。北西へ「こうじヤード」、南東へ「おもちゃのまち」を追加し、働く車で遠出する楽しさと、帰り道を選べる周回性を増やす。

新地区だけを広い空き地にせず、道路、建物、資材、木、標識を既存の純ボクセル玩具表現で配置する。既存仕事の座標・判定・進行は動かさず、追加ミッションなしでも自由走行の目的地として成立させる。

## 4. 採用構成

```text
WORLD X[-48,48], Z[-48,48]

┌───────────────┬─────────┬───────────────┐
│ こうじヤード  │  公園   │               │
│   NW 30×30    │  既存   │               │
├──────┐        ├─────────┼──────┬────────┤
│積み木│        │中央車庫 │      │火災地区│
│ 既存 │        │  既存   │      │  既存  │
├──────┴────────┼─────────┤      ├────────┤
│               │南・色遊び│      │玩具の街│
│               │  既存   │      │SE 30×30│
└───────────────┴─────────┴──────┴────────┘
```

- 既存5地区と主要ランドマークの座標は変更しない。
- こうじヤード: `X[-46,-16] / Z[-46,-16]`、中心`[-31, 0, -31]`。
- おもちゃのまち: `X[16,46] / Z[16,46]`、中心`[31, 0, 31]`。
- 地面外周には2unitの木製余白を残し、箱庭の縁を認識できるようにする。
- 新地区内は四角い周回路、新旧地区間は短い接続路とする。主要経路に行き止まりを置かない。
- 中央車庫から新地区中心までは実入力35秒以内を目標にする。

## 5. 静的mapデータ

`ProductionWorldMapDefinition`を引き続き唯一の座標源とする。

- `WorldDistrictId`へ`construction`と`town`を追加する。
- `landmarks`へ`construction`と`town`の代表中心を追加する。
- 道路は既存12本へ、新地区ごとに内周4本＋既存地区への接続2本を加える。
- visualは既存色を優先し、色group数を不用意に増やさない。
- `validateProductionWorldMap`は新中心が対応地区に属すること、全boxが96×96内であること、ID重複・地区重複がないことを検証する。

## 6. 物理・描画・telemetry

- 地面meshとRapier groundはmap boundsから96×96へ自動導出する。
- 道路と道路線は各1つの`InstancedMesh`を維持する。
- visual boxは同色ごとの固定`InstancedMesh`へまとめる。
- static solidは単一fixed `RigidBody`配下に置き、最大28 colliderとする。
- 新しい毎frame React state、配列生成、Three.js object生成は追加しない。
- `render_game_to_text()`は96×96 bounds、7地区、現在地区、新地区中心、world solid一覧を返す。

## 7. UIアンカーと安全余白

HUDの配置は変更しない。

- 左下joystick、右下action、上中央mission、右上fullscreen／audioをCanvas基準で維持する。
- 新地区の代表ランドマークは、車両を中心へ置いた追従カメラでHUD占有矩形と重ならない配置にする。
- 1280×720、1024×768、844×390の各画面で、Canvas内包、HUD間8px、新地区ランドマークの視認を実寸確認する。

## 8. chunk streaming／LOD判断

今回は96×96ちょうどであり、既定の再検討条件「96×96超」には達しない。追加物は既存batchへ統合し、static colliderも28以下なので、実装時点ではchunk streaming／LODを導入しない。

次のどちらかが成立した場合だけ本タスクを再開する。

1. 最終物理GPU認証でDesktop median 55fpsまたはp10 45fpsを下回る。
2. 将来のworld boundsが一辺96unitを超える。

Docker software rendererのfpsは機能回帰の参考に留め、判断根拠に使わない。

## 11. リスクと対策

| リスク | 対策 |
| --- | --- |
| 広いだけで移動が退屈になる | 2方向接続の周回路と、地区ごとに大きな色・形のランドマークを置く。 |
| 既存仕事の経路が壊れる | 既存5地区・landmark・道路12本の座標を変更しない。 |
| 見た目とcolliderがずれる | `visualBoxes`の`solid`を描画・Rapierで共有し、専用collision E2Eを追加する。 |
| draw callが増える | 既存色へ寄せ、道路・線・visualをInstancedMeshのまま保つ。 |
| world拡張で範囲外復帰が不整合になる | boundsをcanonical mapからのみ導出し、四辺をunit／E2Eで確認する。 |
| 長距離E2Eがflakyになる | district中心直行だけでなく、明示waypointとtelemetry地区edgeを使う。 |

## 12. 性能目標

- Desktop 1280×720の物理GPU: median 55fps以上、p10 45fps以上。
- Tablet／Mobile landscape: 30fps以上を目標とする。
- static collider 28以下、fixed body 1。
- 道路draw call 1、道路線draw call 1、visual draw callは色数以下。
- 既存bundle budget: game 350kB、通常chunk 600kB、Three 750kB、Rapier 2.25MB以内。
- 毎frame React state更新0、追加asset fetch 0。

## 14. ローカル検証結果

2026-08-01のDocker検証では、canonical mapは96×96、7地区、道路24、visual box 55、static solid 27で確定した。追加地区の専用E2Eは1280×720、1024×768 touch、844×390 touchの3画面を一括完走し、こうじヤード68unit、おもちゃのまち71unitで設計上限72unit以内だった。各地区は入口と別出口を実走し、建設事務所と赤い家への衝突もkeyboard／touchで確認した。

HUDは各画面でCanvas内包と主要要素間8px以上を満たし、追加地区6画像を目視して見切れ、重なり、操作阻害がないことを確認した。renderer callは26〜27、static colliderは27で構造予算内だった。

関連unit 94件、全unit 448件、production build、bundle budget、5車種15仕事のfleet E2E、production smokeは成功した。canonical総合E2Eはマップ、左右直進、消火、3画面の実ミッション、放水タイムライン、既存衝突入力を実行し、追加solidの監査理由を更新後にcollision focusも成功した。Docker wall clockとsoftware rendererのfpsは性能認証へ使用しない。

96×96ちょうど、27 collider、既存InstancedMesh構造、追加asset fetch 0のため、chunk streaming／LODは導入しない。96×96版の物理GPU再認証は最終リリース工程で行い、Desktop median 55fps／p10 45fpsを下回った場合だけ再検討する。
