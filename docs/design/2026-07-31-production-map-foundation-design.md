# 72×72本番ボクセル箱庭基盤 設計

## 目的

現在の36×36相当の消防車ゲームを、72×72相当の本番箱庭へ拡張する。
中央車庫をハブとして、北の公園、東の火災地区、西の積み木地区、南の自由走行地区を
道路で接続し、広さを増やしても遊びの密度と目的地の分かりやすさを維持する。

本設計ではモックを追加せず、現在の公開版で受け入れ済みの消防車、消火ミッション、
積み木破壊、固定方向カメラ、HUD、物理契約を本番マップへ移す。

## 採用アプローチ

### 採用: 静的な型付きマップ定義

72×72全域の地区、道路、装飾、solidを型付きデータとして定義し、描画とRapier colliderが
同じ定義を参照する。反復物は色・用途ごとの`InstancedMesh`へまとめ、solidは単一の
fixed `RigidBody`配下へ集約する。

72×72は全域を常時保持できる規模なので、chunk streaming、非同期ロード、LODは導入しない。
毎frameの地区判定は単純なXZ矩形または半径判定とし、React state更新を増やさない。

### 不採用: `VoxelWorld.tsx`へ座標を直接追加

最短で見た目を増やせるが、描画とcolliderのずれ、重複ID、地区追加時の巨大component化を
再発させるため採用しない。

### 不採用: chunk streaming

将来さらに大きくする場合には有効だが、72×72ではロード境界、物理bodyのattach/detach、
telemetry、E2Eを複雑にする方が大きいため採用しない。96×96を超える拡張、または
物理GPUで性能目標を満たせなくなった場合を再検討条件とする。

## 世界観辞書

- 机: 暖かい明色の木製天板。箱庭外周にも余白を残し、巨大な地面に見せない。
- 道路: 濃灰のボクセル道路、黄色の中央線、白い短い横断ライン。
- 中央車庫: 赤白の消防車庫。開始、帰庫再開、将来の乗り換えを担う玩具ハブ。
- 北の公園地区: 芝、池、木、赤黄の遊具。通り抜け可能な空間とsolidを明確に分ける。
- 東の火災地区: 木製ブロック建物、赤橙黄白の玩具炎、黄色い道しるべ。
- 西の積み木地区: 赤、黄、青、緑の破壊可能ブロックと広い復元安全域。
- 南の自由走行地区: 緩い道路カーブ、道路標識、小型の非破壊ブロック景観。
- HUD: 左下の運転スティック、右下の放水、上中央の仕事、右上の全画面を維持する。
- VFX: 水、炎、破片、星の現在の色と時間変化を維持し、写実表現を加えない。

背景、盤面、HUD、ボタン、目的地、文言、エフェクトはすべて「机上の働く車おもちゃ」
という同じ語彙に乗せる。

## マップ座標と地区

座標系は現在と同じく、X正を東、Z負を北とする。

```text
WORLD_BOUNDS = X[-36, 36], Z[-36, 36]

北: 公園地区       X[-12, 12], Z[-34, -14]
西: 積み木地区     X[-34, -14], Z[-10, 16]
中央: 車庫ハブ     X[-10, 10], Z[-10, 10]
東: 火災地区       X[14, 34], Z[-20, 6]
南: 自由走行地区   X[-12, 12], Z[14, 34]
```

- 車庫の基準位置は`[0, 0.8, 6]`とし、正面を北側へ開く。
- 公園の基準位置は`[0, 0, -24]`とする。
- 積み木広場の基準位置は`[-24, 0.18, 6]`とする。
- 火災建物の代表位置は`[26, 1.2, -18]`とする。
- 見える炎の照準点は建物との相対差を維持して`[26.9, 1.45, -16.1]`とする。
- 南地区は今回、新しいミッションを持たない自由走行と将来接続用の余白にする。

中央車庫から東西南北へ幅5unit以上の幹線道路を伸ばし、各地区内の短い周回道路へ接続する。
行き止まりを主要経路に置かず、どの地区からも中央車庫へ別方向から戻れる。

車庫から各既存遊びまでの推奨経路は20〜35秒を目安とする。道路上の目印は火災地区への
現在の道しるべを維持し、他地区は建物の色、地区ゲート、道路標識で方向を読めるようにする。

## アーキテクチャ

```text
worldLayout.ts
  ├─ PRODUCTION_WORLD_MAP
  ├─ WORLD_BOUNDS
  ├─ GARAGE_POSITION
  ├─ FIRE_POSITION / FIRE_SPRAY_TARGET_POSITION
  ├─ PARK_CENTER / BLOCK_PLAZA / BREAKABLE_BLOCKS
  └─ 地区判定pure helper
          ↓
worldCollisionLayout.ts
  └─ 同じmap定義からsolid collider planを構成
          ↓
VoxelWorld.tsx
  ├─ 道路・線・地面をInstancedMeshで描画
  ├─ 地区ごとの視覚component
  └─ 単一fixed bodyへsolid colliderを接続
          ↓
VoxelGameScene / VoxelGameApp
  ├─ 現在地区・目的地区telemetry
  └─ 既存runtime、入力、カメラ、HUDを維持
```

### データ境界

`WorldMapDefinition`は少なくとも次を持つ。

- `bounds`
- `districts`
- `roadSegments`
- `roadMarkings`
- `landmarks`
- `solidBoxes`

すべての定義は一意な`id`、world座標、scale、用途を持つ。
描画componentは座標を追加定義せず、定義を表示へ変換する。
collider planも見た目と同じsolid定義を使い、別座標の複製を禁止する。

ゲームプレイで既に参照される`GARAGE_POSITION`、`FIRE_POSITION`、
`FIRE_SPRAY_TARGET_POSITION`、`BREAKABLE_BLOCKS`は、map定義から導出した公開定数として
維持し、runtimeやVFXへmap全体を依存させない。

## データフロー

1. 起動時に本番マップ定義のID、境界、scale、地区重複、主要地点を検証する。
2. `VoxelWorld`が同じ定義から地面、道路、建物、装飾を描画する。
3. `WorldSolidColliders`がsolid定義だけを単一fixed bodyへ接続する。
4. 車両位置からpure helperが現在地区を低頻度で判定する。
5. runtimeのミッション、消火、破壊、帰庫再開は導出済み主要座標を使用する。
6. telemetryは現在地区、目的地区、world bounds、既存の車両・火・破壊状態を返す。

## 物理・カメラ・HUD

### 物理

- world境界を±36へ広げ、車両の落下・範囲外復帰判定も同じ境界を使う。
- 地面は72×72を覆う単純形状とし、道路ごとの物理bodyを作らない。
- 車庫壁、火災建物、公園遊具、木の幹、地区ゲート、南地区の道路標識をsolidにする。
- 道路線、道しるべ、樹冠、窓、屋根装飾、水、炎の表示、星は非solidにする。
- 見た目上、車両の高さまで立ち上がる障害物は、上記の非solid明示対象を除きcolliderを持つ。
- static colliderは単一fixed bodyへ集約し、動的bodyは車両と破片poolだけを維持する。

### カメラ

固定した世界方向と車両追従を維持する。72×72全景を一度に収めるためにzoomを下げず、
現在の車両、進行方向、近いランドマークが見える注視点を守る。

### HUDアンカー

- 運転スティック: Canvas左下＋safe area。
- 放水: Canvas右下＋safe area。
- 仕事表示: Canvas上中央。
- 全画面: Canvas右上＋safe area。

マップの主要ランドマークはHUD占有矩形へ常時固定しない。
カメラ追従中の車両と次の道しるべが、HUDの内側安全矩形に入ることを代表viewportで確認する。

## エラー処理

- 重複ID、非有限座標、負または0のscale、world境界外の主要地点は起動前検証で拒否する。
- solid定義に対応する見た目が存在しない場合、unit testで失敗させる。
- 地区判定へ非有限座標が渡された場合は`outside`を返し、例外やNaNを描画へ伝播させない。
- collider ref未準備のframeは既存どおり操作せず、次の同期で正しい状態へ合わせる。
- world外へ出た車両は中央車庫へ安全復帰し、入力と速度をリセットする。

## テスト方針

### Unit

実装コードより先に次を失敗するtestとして追加する。

- `WORLD_BOUNDS`が72×72で、全主要地点とdistrict boundsを含む。
- 地区ID、道路ID、ランドマークID、solid IDが一意である。
- scaleと座標が有限で、scaleが正である。
- 中央車庫から4地区へ幅5unit以上の道路接続がある。
- 地区判定が境界内、境界上、境界外、非有限値を正しく扱う。
- 見た目とsolidが同じ共有定義を参照する。
- 車庫正面の退出路と帰庫領域がsolidへ重ならない。
- 消火位置と照準点の相対差、積み木間隔、破壊pool数を維持する。

### Integration

- `VoxelWorld`が本番マップ定義の地区・道路・solidを各1回だけ接続する。
- `VehicleController`が±36の境界と新しい車庫位置を使う。
- `WaterAndFire`が移設後の見える炎へ既存条件で照準する。
- `VoxelGameRuntime`の消火、成功、自由走行、帰庫再開を変更しない。
- telemetryが現在地区と目的地区を返す。

### Browser E2E

- 中央車庫から火災地区へ移動し、寛容な照準で消火を完了する。
- 火災地区から中央車庫へ帰り、同じ仕事を再開する。
- 中央車庫から積み木地区へ移動し、指定ブロックを壊して安全復元を確認する。
- 北公園、東建物、西積み木、南標識、車庫壁を貫通しない。
- world境界外へ押し出された車両が中央車庫へ復帰する。
- Desktop 1280×720、tablet landscape 1024×768、mobile landscape 844×390で確認する。
- console error、page error、request error、契約違反を0件にする。
- 代表画像を目視し、道路接続、地区密度、HUD重なり、colliderと見た目の対応を確認する。

## 受け入れ条件

- 72×72相当の1枚続きの箱庭として中央ハブと4地区を走行できる。
- 車庫から消火・破壊の既存遊びへ20〜35秒を目安に到達できる。
- 既存の消火完走、成功演出、自由走行、帰庫再開が機能する。
- 既存の積み木破壊、破片、車両が離れた後の安全復元が機能する。
- 車庫、公園遊具、木の幹、火災建物、地区ゲート、南地区標識を貫通しない。
- 道路線、道しるべ、樹冠、窓、屋根装飾、水、星は意図どおり非solidである。
- 固定方向カメラで進行方向と近いランドマークを見失いにくい。
- HUDの操作要素が3 viewportでCanvasとsafe area内に収まり、車両操作を妨げない。
- `render_game_to_text()`がworld bounds、現在地区、目的地区、既存ゲーム状態を返す。
- Docker内のunit test、type checkを含むproduction build、フルE2Eが成功する。
- console、page、request errorが0件である。
- 物理GPUでDesktop 60fps目標、tablet・mobile landscape 30fps以上を維持する。

- 消防車の追加ミッション、複数火災、ランダムイベント。
- 色付きプール、色付きシャワー。

## リスクと対策

| リスク | 対策 |
| --- | --- |
| 広いだけで移動が退屈になる | 4方向へ遊びを分散し、20〜35秒の到達目安、周回路、途中の標識を固定する。 |
| 座標移設で消火や帰庫判定が壊れる | 主要位置をmap定義から導出し、相対差と状態遷移をunit・E2Eで固定する。 |
| 見た目とcolliderがずれる | solidの共有定義を描画とRapierで共用し、重複座標を禁止する。 |
| `VoxelWorld`が再び巨大化する | 地区とrender planをデータへ分離し、React componentは変換だけを担う。 |
| draw callとcolliderが増える | 反復物をInstancedMeshへまとめ、static colliderを単一fixed bodyへ集約する。 |
| 全景を見せようとして車両が小さくなる | zoomを下げず、固定方向の局所追従とランドマーク・標識で案内する。 |
| E2E経路が長く不安定になる | 地区単位の短いscenarioへ分け、resetと決定的telemetryを使う。 |
| モバイルで遠景負荷が増える | 同じ技術予算で3 viewportを計測し、必要時は装飾密度だけを段階的に落とす。 |

## 性能目標

- Desktop 1280×720: 物理GPUで60fpsを目標にする。
- Tablet landscape / Mobile landscape: 物理GPUで30fps以上を目標にする。
- static colliderは単一fixed bodyへ集約し、合計32個以内を初期予算とする。
- 地区の反復形状は個別meshにせず、用途とmaterialごとのInstancedMeshへまとめる。
- 車両、炎、放水、破片の既存poolとbatch数を増やさない。
- 毎frameのReact state更新、配列生成、Three.js object生成を追加しない。
- Docker SwiftShaderのfpsは機能回帰の参考に限定し、性能認証に使わない。
