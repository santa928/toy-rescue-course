# 純ボクセル消防車ゲームプレイ縦切り設計

## 目的

承認済みの純ボクセル消防車を実際に運転できる新規ゲーム基盤へ接続し、消火ミッションと積み木破壊を含む最小のプレイ体験を検証する。

新規実装は既存ゲームと混ぜず、独立した `voxel-game.html` と `src/voxel-game/` に構築する。縦切り版が受け入れ条件を満たすまでは既存ゲームを比較対象として維持する。

## 採用アプローチ

新しい `voxel-game.html` をViteの独立エントリとして追加する。旧 `index.html`、旧シーン、旧HUDは変更せず比較用に残す。

既存実装を直接置き換える方式は、旧車両表現、地形、物理、巨大なシーン責務との密結合を引き継ぐため採用しない。全面削除から始める方式も、手触りを確認する前の変更範囲が大きいため採用しない。

## 世界観辞書

- 車両: 承認済みの短く太い純ボクセル消防車。640セル、赤、白、黒、銀、青、橙、濃灰の7色。
- 地面: 暖かい木目の机。箱庭の外周まで机上玩具として読める色と照明にする。
- 道路: 濃い灰色の周回道路と黄色の中央線。滑らかなテクスチャではなくボクセル面で作る。
- 公園: 明るい緑の芝、水色の池、木製遊具、立方体で構成した木。
- 車庫: 白と赤の消防車庫。開始地点、再出発地点、将来の乗り換え拠点を兼ねる。
- 火災現場: 木製ブロック建物、橙と黄色のボクセル炎。写実的な煙や流体は使わない。
- 放水: 水色から白へ変わる小さなボクセル列。火へ軽く曲がるが、真横や背後には曲がらない。
- 破壊: 指定積み木だけが数個のボクセル片へ崩れる。破片は短時間だけ転がって消える。
- 道しるべ: 道路上に並ぶ黄色い発光ボクセル。目的地到着時に消える。
- HUD: 玩具の操作パネル。文字を減らし、左スティック、右放水、上部の仕事アイコンに絞る。
- 演出: 成功時はボクセルの星と短い「できた！」だけを表示する。写実的な粒子、星評価、通貨は使わない。

## 箱庭レイアウト

36×36相当の高密度な1区画を作る。

- 下側: 消防車庫と開始位置。
- 中央: 池と遊具のある公園。
- 右上: 最初の火災現場。
- 左側: 崩せる積み木広場。
- 外周: すべての主要地点へ接続する周回道路。
- 道しるべ: 車庫から火災現場までの道路上だけに表示する。

将来の72×72前後の箱庭は、周回道路の外側へ区画を接続して拡張する。縦切り段階では移動時間より遊びの密度を優先し、車庫から火災現場まで1分以内に到達できる距離にする。

## プレイループ

1. 消防車庫から開始し、消火の仕事と黄色い道しるべが自動で現れる。
2. プレイヤーは火災現場へ向かうか、積み木広場へ寄り道する。
3. 火災現場で放水を当てると、火の強さと炎のボクセル段階が減る。
4. 2〜3秒相当の有効放水で消火が完了する。
5. ボクセルの星と「できた！」を短く表示し、自由走行へ戻る。
6. 車庫へ戻ると火災と道しるべを初期化し、同じ仕事を再開できる。

ゲームオーバー、失敗、時間切れ、点数、星の個数評価は設けない。

## 操作・カメラ・HUD

### 操作

- PC: 矢印キーまたはWASDで前進、後退、旋回する。Spaceで放水する。
- タッチ: 左下のスティックで運転し、右下の放水ボタンを長押しする。
- 入力装置の違いは共通の `DriveInput` と `ActionInput` へ正規化する。

### 放水

放水は消防車の前方から発射する。一定距離内かつ前方コーン内に火がある場合だけ、放水方向を軽く補正する。範囲外、真横、背後の火へは追尾しない。火がない場所でも放水表現は出し、ボタンへの反応を常に返す。

### カメラ

高めの斜め固定視点を使い、車両位置だけを滑らかに追従する。世界の北方向を画面上で固定し、車両の旋回によってカメラを回転させない。車両、目的地、道路の先が見える注視点と安全余白を維持する。

### HUDアンカー

- 左スティック: Canvas左下とsafe areaへ固定する。
- 放水ボタン: Canvas右下とsafe areaへ固定する。
- 仕事表示: Canvas上端中央へ固定する。
- 主要3Dオブジェクト: HUD占有領域を避けたカメラの安全矩形内に置く。

固定比率で配置せず、Canvas境界、safe area、各操作要素の実寸から余白を決める。

## アーキテクチャ

```text
src/voxel-game/
├── domain/       # ミッション、火、破壊・復元のpure logic
├── input/        # キーボード、タッチ、共通入力状態
├── physics/      # Rapier車両制御、衝突イベント、復帰処理
├── scene/        # 箱庭、消防車、火、放水、積み木、カメラ
├── ui/           # 仕事表示、スティック、放水ボタン
├── VoxelGameApp.tsx
├── main.tsx
└── styles.css
```

### 責務

- `domain`: Three.js、React、Rapierへ依存しない。時間入力から次状態を返す。
- `input`: 入力装置を共通状態へ変換し、複数入力の同時押し解除を保証する。
- `physics`: 車両の剛体、加速、旋回、衝突、転倒・落下時の車庫復帰を扱う。
- `scene`: 3Dオブジェクトの生成と視覚表現だけを扱う。
- `ui`: 低頻度なゲーム状態を表示し、操作イベントを入力層へ渡す。

## データフロー

```text
キーボード / タッチ
  → 共通入力状態
  → Rapier車両制御
  → 車両位置・速度・向き
  → 放水判定 / 衝突判定
  → pureな火・積み木・ミッション状態
  → 3D表現とHUD
```

車両位置や速度はrefとRapier APIで管理し、React stateへ毎フレーム同期しない。Reactへ渡すのはミッション段階、消火完了、積み木復元など低頻度の状態だけにする。

## 物理と破壊

- 消防車の視覚モデルは承認済み640ボクセルを7つの`InstancedMesh`で描画する。
- 車両物理はボクセルごとに持たず、車体全体を覆う単純な複合コライダーを使う。
- 指定積み木は衝突速度が閾値を超えたときだけ壊れる。
- 破片は上限付きプールから取得し、短時間後に非表示化して再利用する。
- 元の積み木は約5秒後、車両が復元領域外にいる場合だけ復元する。
- 車両が箱庭外へ落下または長時間復帰不能になった場合は消防車庫へ戻す。

## エラー処理

- ボクセルモデルは起動時に重複座標、palette、セル数を検証し、不正時は明確なエラーを出す。
- 入力のpointer cancel、blur、visibility changeで押下状態を解除する。
- Mission stateに不正な遷移が要求された場合は状態を変更せず、開発時ログへ理由を残す。
- 物理オブジェクトのrefが未準備の場合は更新をスキップし、次frameで再試行する。
- ネットワーク、セーブ、外部APIは本縦切りに含めない。

## 決定的な検証フック

`window.render_game_to_text()` は少なくとも次を返す。

- 座標系の説明。
- mission phase、現在の目的地、完了状態。
- 車両位置、向き、速度、転倒・復帰状態。
- 放水中か、追尾対象、火の強さ。
- 壊れている積み木と復元までの残り時間。

`window.advanceTime(milliseconds)` はpure domain clockを固定stepで進め、消火と復元を自動テスト可能にする。Rapierのブラウザ操作検証は短い入力burstと状態観測を組み合わせる。

## 受け入れ条件

- 車庫から消火完了、自由走行、車庫での再開までをPCとタッチで完走できる。
- 放水の自動追尾は近距離かつ前方の火だけに反応する。
- 指定積み木だけが有効な衝突で崩れ、安全な条件で復元する。
- 画面固定方向の追従カメラで運転中の方向を見失いにくい。
- 純ボクセル消防車の見た目がVehicle Labの承認版から崩れない。
- 道路、建物、公園、火、水、道しるべ、破片が世界観辞書へ一致する。
- HUDが主要オブジェクトを隠さず、各操作要素が親境界とsafe area内に収まる。
- `render_game_to_text()` と `advanceTime()` でミッション、車両、火、積み木を検証できる。
- Docker内のunit test、type checkを含むbuild、Playwright E2Eが成功する。
- Desktop 1280×720、tablet landscape 1024×768、mobile landscape 844×390で画面を目視確認する。
- Console errorとpage errorが0件である。
- 旧ゲーム、Vehicle Lab、新Voxel Gameの3エントリが同時にbuild・起動できる。

## 非対象

- 最終72×72前後の全箱庭。
- 消防車以外の車両、車両選択、乗り換え。
- 色プール、色シャワー。
- 複数ミッション、ランダムイベント。
- セーブ、進行、通貨、解除、ランキング。
- 音声、音楽、ボイス。
- 写実的な流体、煙、炎、post-processing。
- 旧ゲームの削除と新ゲームの `/` 昇格。

## リスクと対策

| リスク | 対策 |
| --- | --- |
| 640ボクセル車両でdraw callが増える | 色別7バッチを維持し、個別meshを作らない。 |
| 破片物理が増えて性能が落ちる | 破片数と寿命へ上限を設け、poolで再利用する。 |
| カメラ固定で進行方向が分かりにくい | 車両前方の道路を含む注視点と道しるべで補助する。 |
| 自動追尾が勝手に感じる | 前方コーンと短距離へ限定し、補正角度を小さくする。 |
| 積み木が車両の下へ復元する | 復元領域から車両が離れていることを必須にする。 |
| RapierとReact stateが競合する | 高頻度状態をrefへ閉じ、pure domainとの同期点を限定する。 |
| 旧実装と新実装が混ざる | 独立entryと`src/voxel-game/`境界を守る。 |

## 性能目標

- Desktop 1280×720: 物理GPUで60fpsを目標にする。
- Tablet landscape / Mobile landscape: 30fps以上を目標にする。
- 消防車: 640ボクセル、車両本体7 draw callsを維持する。
- 破片: 同時表示数に固定上限を設ける。
- GPU時間を取得できない環境ではCPU側rAF値とrenderer情報を記録し、物理GPU性能を認証したとは扱わない。

## 新規方針の採用と旧実装削除

本設計の受け入れ条件を満たし、ユーザーが実際の操作感と見た目を承認した場合、新規方針を正式採用する。

採用後は次の順で移行する。

1. 新しいVoxel Gameを `/` へ昇格する計画を作る。
2. 旧シーン、旧車両、旧HUD、旧ゲーム固有stateの削除候補を参照確認付きで一覧化する。
3. Vehicle Lab、共通Voxel model、テスト基盤など残す部品を明示する。
4. 削除対象と影響をユーザーへ提示し、明示承認を得る。
5. 削除後に参照残りチェック、3エントリから移行後構成へのbuild、主要画面スモークを行う。

縦切り実装中には旧コードを削除しない。
